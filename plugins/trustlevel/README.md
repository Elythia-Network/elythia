# trustlevel

利用実績に応じてロールを自動付与するプラグイン。

インスタンスの base policy を控えめにしておき、条件を満たしたローカルユーザーへ
運営者が指定したロールを付ける。段階的に機能を開放したいときに使う。

**#2585 の検証台として作った** (#2586)。新しい公開面を足さずにどこまで書けるかを
確かめるのが目的で、足りなかったものは末尾に記録している。

## 動かす

```bash
# Elythia のリポジトリルートで
make build     # plugins/ を走査してビルドに取り込む
```

`plugins/` に置いても**既定では無効**。`mk-plugin.yml` に `disabled: true` があり
`make build` の対象から外れる (同梱サンプルなので、clone しただけの人のビルドに
勝手に入らないようにしてある)。有効にするには `disabled: true` の行を消す。

**下の設定だけを書いても動かない。** ビルドに取り込むのが先。

**管理画面 (`frontend/AdminPage.vue`) を出すにはフロントの再ビルドも要る。**
`make build` が呼ぶ `pluginbuild` は取り込み先の TypeScript を生成するだけで、
vite ビルドまでは走らない。手順は環境ごとに違うので [デプロイ](../../docs/deployment.md)
を見ること。

**手元で動かしてみるだけなら `make plugin-dev PLUGIN=plugins/trustlevel`。**
tracked ファイル (`mk-plugin.yml`) を編集せずに済む。`disabled: true` を消して
push すると、同梱サンプルが既定無効であることを見る CI (`build` job の
`Check bundled plugins are disabled by default`) が落ちる。

## policy を持たない

判定結果はロールとして `admin/roles/assign` で永続化し、プラグインは判定状態しか
持たない。

解決時に policy を差し込む形にすると、Misskey TS へ切り替えた瞬間にプラグインが
消えて**利用者の権限が黙って変わる**。ロールなら切り替えても残り、プラグインを
止めても最後に確定した状態が生きる。

Elythiaは`EffectivePolicies`も提供するが、この判断は変わらない。trustlevelの目的は
一度確定した昇格を停止・切り戻し後も維持することで、解決時だけの動的な値ではない。
providerはlevel連動値など、ロール付与だけでは表現できず、停止時に消えることを
運営者が受け入れた用途に使う。

緩和方向にしか動かさないので、判定が失敗しても昇格しないだけで済む。

## 設定

```yaml
plugins:
  trustlevel:
    roleId: "9abc..."             # 付与するロールの ID (必須)
    actorId: "9def..."            # 実行主体になる管理者の ID (必須)
    minAccountAgeDays: 7          # 作成からの経過日数
    minNotes: 10                  # ノート数
    cron: "0 * * * *"             # 実行間隔 (5 フィールド、UTC)
    pageSize: 100                 # 1 回の取得件数 (1〜100)
```

**両方とも空なら何も登録せず起動を続ける** (`Info` ログで設定が要ることだけ伝える)。ビルドに取り込んだ時点で有効になる (実行時の `enabled` は既定 true) ので、未設定で起動を止めると、`disabled: true` を消しただけのインスタンスが全断するため。

**片方だけを書くと起動時に落ちる。** 書き途中か書き間違いなので、黙って何もしないと運営者は「設定したのに昇格しない」を延々と追うことになる。

### 実行主体について

管理操作は `actorId` の管理者の権限で行う。Elythia には「すべてを迂回する」経路が
無いため (#2476)、必ず誰かの権限で実行される。

このため次の 2 点に注意する。

- **モデレーションログがこの管理者の操作として積まれる。** 自動付与の分が人手の
  操作と混ざるので、`cron` を短くしすぎると読みにくくなる
- **この管理者が凍結・降格・削除されると昇格が止まる。** 止まったことは管理画面の
  「失敗」件数と各利用者の `lastError` で分かる

### 付与時の通知

`isPublic` なロールを付けると、Elythia が本人へ通知を送る。段階開放を利用者に
知らせたいなら公開ロール、静かに広げたいなら非公開ロールにする。

## 判定

すべて満たしたときに付与する。

- ローカルユーザーである
- 凍結されていない
- 作成から `minAccountAgeDays` 日以上経過している
- ノート数が `minNotes` 以上
- 手動で保留されていない

**作成日時が読めない利用者は付与しない。** 不明を有利に倒さない。

一度付与したら外さない。剥奪は運営者が `admin/roles/unassign` で行う。

## 冪等性

毎回 `admin/show-users` から現在値を読み直すので、何度走らせても結果は同じ。

既に付与済みの利用者への `admin/roles/assign` は 409 (`ALREADY_ASSIGNED`) を
返すが、**これは目的の状態なので成功として扱う**。異常系にすると reconcile の
たびに失敗が積み上がる。

`expiresAt` は渡さない。期限付き付与だと TS へ切り替えた後に失効し、プラグインが
居ないので再付与されない。

## 管理 API

`/api/plugin/trustlevel/` 配下。いずれもモデレーター以上。

| endpoint | 内容 |
|---|---|
| `POST admin/overview` | 設定・件数 (合計 / 付与済み / 保留 / 失敗) と直近 10 回の実行記録 |
| `POST admin/subjects` | 判定状態の一覧 (`filter`: `granted` / `held` / `failing`) |
| `POST admin/hold` | 手動保留の切り替え |

## 実行記録

1 周ごとに走査件数・付与件数・失敗件数・所要時間を `runs` に残す。
サブ issue を切るときの根拠にするため、「遅い気がする」ではなく実測を見せる。

## 既存の公開面で足りたか (#2586 の検証結果)

**足りた。本体は 1 行も変更していない。**

使ったもの:

| 公開面 | 用途 |
|---|---|
| `Definition.Migrations` / `Storage` | 判定状態と実行記録 |
| `Jobs.Schedule` / `Handle` | 定期 reconcile |
| `Config` | しきい値・対象ロール・実行主体 |
| `API().AsUser()` | `admin/show-users` / `admin/roles/assign` |
| `Router` / `Request` | 管理 API |
| `Request.IsModerator()` | 管理 API の認可 |
| `APIError.Status` | 409 の判別 |

使わなかったもの: `Peer` (連合しない)、`Blob`、`Anonymous`。

### 気づいた点

- **`admin/show-users` の `limit` 上限が 100** (`pagination.ResolveLimit`)。全体
  reconcile は offset 送りになる。利用者が増えたとき、ここが最初に効いてくる。
  実測は管理画面の実行記録で見られるので、**負荷が実際に問題になってから**
  domain event を検討する
- **`APIError.Status` で 409 を判別できた。** ここが取れないと「既に付与済み」を
  エラー本文の文字列一致で判定することになっていた
- **`plugin.Caller` は endpoint 名を文字列で取る。** 型付けは無いが、生 JSON を
  返す設計と揃っていて、upstream の項目増減に巻き込まれない利点の方が大きい

### 足りなかったもの

現時点では**無い**。ユーザー管理画面から判定状態を見られないのは不便だが、
独自の管理ページで代替できている。#2585 の frontend slot は、この不便が実運用で
残るかを見てから判断する。

## 実測 (go.k7a.org / ローカル 16 人)

5 分間隔で 5 周ぶん。

| 周 | 走査 | 付与 | 失敗 | 所要 |
|---|---|---|---|---|
| 初回 | 16 | 4 | 0 | 107 ms |
| 2 周目 | 16 | 0 | 0 | 27 ms |
| 3 周目 | 16 | 0 | 0 | 23 ms |
| 4 周目 | 16 | 0 | 0 | 46 ms |
| 5 周目 | 16 | 0 | 0 | 27 ms |

空振りの中央値 27 ms。判定内訳はノート数不足 8 / 作成日数不足 3 / 凍結 1 / 付与 4。

**モデレーションログは初回の 4 件だけで、以降は増えない。** 付与済みは
`subjects.granted` を見て早期に返すので `admin/roles/assign` を呼ばない
(409 に頼るまでもない)。ロール付与も 4 件で止まっており、冪等に回っている。

### domain event は要るか

**現時点では要らない。**

- `admin/show-users` の 100 件上限に当たるのは 100 人から。16 人は 1 ページで
  収まり、走査全体で 27 ms。仮に 1,000 人でも 10 ページで、単純比例なら 1 秒弱。
  5 分間隔に対して十分小さい
- 条件が「作成から 7 日」「ノート 10 件」なので、**最大 5 分の遅延が実害にならない**。
  秒単位に縮める必要が見当たらない

再評価が要るのは、走査の所要時間が実行間隔に対して無視できなくなったとき
(利用者数が数千規模になる、あるいは条件に重い API 呼び出しが増える)。
その判断は上の `runs` を見て行う。
