## リリース全体の性格

minor release で、backend は小さな不具合の修正 (ストリーミング 2 件、Web Push、連合の引用、キューの設定の検査) と、ドライブの一覧の性能の修正、`meta` の既定値を揃える migration が中心。本家の動作要件の変更 (Node.js 22 のサポート終了、最低版を 24.22.3 / 26.13.1 へ、起動用の `scripts/start.mjs`) は Node で動く本家に固有で、Elythia では frontend のビルドに使う Node だけに関わる。

### 1. `meta` の 3 列の既定値を揃える (#18140)

- upstream: `5163caea12`。新しい migration `FixMetaMigratedConfigColumnDefaults1794385801836` が、`meta` の `proxyRemoteFiles` / `signToActivityPubGet` / `allowExternalApRedirect` の `DEFAULT` を `true` にする。既存の行の値は変えない
- 経緯: 旧 migration `migrateSomeConfigFileSettingsToMeta1746949539915` は、2025.5.1 (#16026) で設定ファイルの値を `DEFAULT` に焼き込む形で入り、2025.12.0 (#16929) で `DEFAULT TRUE` に変わった (2026.10.1 も `TRUE`)。2026.11.0 の compile-config の revert (`b6b3f6279f`) が、`migration/js/migration-config.js` を足して旧 migration を設定ファイルの値に頼る形へ戻したので、どの版で流したかで `DEFAULT` が揺れる。#18140 はそれを新しい migration で `true` に揃える (版を含む tag は `git tag --contains` で確かめた)

**Elythia は部分対応。** Elythia が作る DB は 3 列とも `DEFAULT true` (`migration/000001_initial.up.sql:418-419`、`migration/000029_db_compat_misskey.up.sql:121`、`internal/model/meta.go:135,139,233`)。TS 版から引き継いだ DB のうち、旧 migration を TS 2025.5.1〜2025.11.x で流したものは、当時の設定ファイルの値が `DEFAULT` に残る (`proxyRemoteFiles` を設定していなければ `false`、`signToActivityPubGet: false` や `disallowExternalApRedirect: true` を設定していればその値)。2025.12.0 以降に流した DB は `true`。Elythia は `meta` の行を作るときに DB の既定値に頼る (`internal/repository/meta.go:139` は ID・RepositoryURL・FeedbackURL の 3 列だけを書く) ので、既定値を揃える意味がある。

- 対応: 新しい migration に、3 列の `ALTER COLUMN ... SET DEFAULT true` (冪等) と、`migrations` テーブルへの `FixMetaMigratedConfigColumnDefaults1794385801836` の記録を入れる。DDL を先に入れてから名前を書く (`migration/000135_migrations_typeorm_names_2026_10_1.up.sql` と同じ方針)
- `TestMigrationSeed_CoversUpstream` (`internal/entitycompat/migration_seed_test.go`) が `testdata/golden_upstream_migrations.json` と突き合わせるので、版を上げると名前の漏れで落ちる。golden は `go run ./tools/schemadrift` で作り直す

### 2. ドライブのルートのファイル一覧が遅くなる (#18129)

**Elythia は未対応。** `internal/repository/drive_file.go:328-372` の `ListByUser` は、`"folderId" IS NULL` の後に `ORDER BY id` で並べており、本家の修正前と同じ形。さらに、**Elythia が作る DB には本家の `(userId, folderId, id)` の index `IDX_55720b33a61a7c806a8215b825` が無い** (migration には `IDX_drive_file_userId` (`000001:114`) だけ)。

- 対応: 本家と同じ名前で `CREATE INDEX CONCURRENTLY IF NOT EXISTS "IDX_55720b33a61a7c806a8215b825"` を足す (同じ名前なので `TestIndexNaming_NoNewUpstreamDuplicates` に掛からない。TS 版から移した DB では既にある)。ルートの一覧で、並べ替えが既定か `createdAt` のときは `ORDER BY "folderId" <向き>, id <向き>` にする。EXPLAIN で index を使うことを確かめるテストを付ける。難易度 M

### 7. ジョブキューの同時実行数の設定が不正なら、起動時に止める (#18081)

### 推奨実行順 (Wave)

追従は 1 PR にまとめ、段階ごとにコミットを分ける ([`../upstream-catch-up.md`](../upstream-catch-up.md) の 2 章)。各コミットが単体でビルドとテストを通す順に並べる。

- **Wave 1 (frontend の取り込み)**: `tools/upstreamsync` に `docs/contributing/` の区分を足し、`make upstream-sync TO=2026.11.0` で `frontend/` に当てる。衝突の解消 (本家が同じ問題を直したものは本家の形を採る)、`pnpm-lock.yaml` の作り直し、Node 26.13.1、Playwright の設定の表と en-US の許可リスト
- **Wave 2 (S の backend)**: 5 (Web Push) → 7 (キューの設定) → 3 (ローカルタイムライン) → 6 (引用の「RE:」)
- **Wave 3 (M の backend)**: 2 (ドライブの一覧。index と並べ方) → 4 (アンテナの `isVoted`)
- **Wave 4 (版を上げる)**: `UPSTREAM_MISSKEY_VERSION`・`MisskeyVersion`・e2e の TS の image を 2026.11.0 に上げ、golden を作り直す (`make shapecheck-gen` / `make paramdef-gen` / `make upstream-check`)。同じコミットで 1 (migration と seed)、8 (divergence の記録)、compile-config の revert への追従、`docs/divergence/db.md` の件数を入れる

本家の版を上げた後に必須の作業は [`../upstream-catch-up.md`](../upstream-catch-up.md) の「本家の版を上げた後に必須」の各節を参照。
