# 1.5.0 から 2.0.0 へ上げる

2.0.0 は、名前を mk-go から **Elythia** に変えた版。リポジトリ・配布イメージ・実行バイナリ・frontend の置き場所がまとめて変わるので、構成ごとに手で直すものがある。この文書は、1.5.0 で動いているインスタンスを 2.0.0 へ上げる手順を、構成ごとに上から順に流せる形でまとめたもの。

個々の変更の背景は [デプロイ](../deployment.md#アップデート) の各節にある (この文書はそこから手順だけを抜き出している)。

## 何が変わるか

| | 1.5.0 | 2.0.0 |
|---|---|---|
| リポジトリ | `github.com/shiroha-a/mk` | `github.com/Elythia-Network/elythia` (旧 URL は GitHub が転送する) |
| 配布イメージ | `ghcr.io/shiroha-a/mk` | `ghcr.io/elythia-network/elythia` (旧イメージは更新が止まっている) |
| 実行バイナリ | `misskey` / `migrate` / `backfill-<名前>` | `elythia` 1 つ。`elythia serve` / `elythia migrate` / `elythia backfill <名前>` など |
| frontend のソースとビルドの出力先 | submodule `third_party/misskey` → `third_party/misskey/built` | 本体の `frontend/` → `frontend/built` |
| nodeinfo の `software.name` / User-Agent | `mk-go` / `mk-go/<版> (<url>)` | `elythia` / `Elythia/<版> (<url>)` |
| プラグインのマニフェスト | `mk-plugin.yml` | `elythia-plugin.yml` |
| プラグインが import するパス | `github.com/shiroha-a/mk/plugin` | `github.com/elythia-network/elythia/plugin` |
| nodeinfo のプラグインの宣言 | `metadata.mkGoPlugins` | `metadata.elythiaPlugins` |

変わらないもの: DB のデータ (移行は要らない)、設定ファイルの書式、環境変数の接頭辞 `MK_`、`/api/meta` の `mkGoVersion` / `mkGoCommit`、compose の project 名 (volume はそのまま使える)。

migration は 8 本増える (`000109`〜`000116`)。`000109`〜`000115` は画像プロキシの許可確認のための index を `CONCURRENTLY` で作るもの、`000116` は `meta.repositoryUrl` / `meta.feedbackUrl` のうち以前の既定値のままの行を新しい URL にするもの。**どれも 1.5.0 のサーバーがそのまま動ける変更なので、1.5.0 を動かしたまま先に流してよい** (C の手順 6 と D の手順 4 でそうしている。A / B は `migrate` サービスが `up -d` のときに流すので、index を作り終えるまで Elythia は起動しない)。index の作成は、`user` / `drive_file` / `emoji` / `instance` の行数に比例して時間がかかる。

ただし、**先に流した後は 1.5.0 を起動し直さないこと。** 1.5.0 の `migrate` は自分の知らない版 (`116`) まで進んだ DB に当たると止まるので、起動のたびに migration を流す構成 (C の UDS) では、1.5.0 のコンテナが再起動した時点で起動できなくなる。先に流したら、そのまま 2.0.0 へ切り替える。

1.5.0 を動かしたまま `000116` を流すと、1.5.0 の `/about-mkgo` に同じリポジトリが 2 行並ぶ (1.5.0 は以前の URL を本体の URL として持っているため)。見た目だけで、2.0.0 へ切り替えれば 1 行に戻る。

## 上げる前に (全構成で共通)

1. **DB をバックアップする。** 2.0.0 は DB の形を壊さないが、上げる作業の失敗に備える

   ```bash
   # Docker Compose (TCP / docker ブランチ)
   docker compose exec -T db pg_dump -U <user> -Fc <db> > before-2.0.0.dump
   # Docker Compose (UDS)
   docker compose -f compose.uds.yaml exec -T postgres pg_dump -U <user> -Fc <db> > before-2.0.0.dump
   # バイナリ直接実行
   pg_dump -h <host> -U <user> -Fc <db> > before-2.0.0.dump
   ```

2. **プラグインを `plugins/` に置いているなら、2.0.0 に追従した版があるかを確かめる。** 2.0.0 はモジュールパスとマニフェストの名前が変わったので、追従していないプラグインがあるとビルドが止まる (`disabled: true` で外しているものも止まる)。同梱プラグイン (`status` / `trustlevel`) と、`Elythia-Network/elythia-plugin-*` の 4 つ (fedwatch / genshin / hsr / nowplaying) は追従済み。自分で書いたプラグインの直し方は [プラグインの互換性](../plugins/compatibility.md#go-のモジュールパスの変更-3394) と [マニフェストの改名](../plugins/compatibility.md#マニフェストの改名-3400)
3. **Misskey TS へ戻すことは保証しない** (#3191)。2.0.0 で、TS へ戻せること (復路) の保証をやめた。戻す可能性があるなら、上げる前に [TS版からの移行](../migration-from-ts.md#misskey-tsへのロールバック) を読む

**どこまで進むかは、追っているブランチで決まる。** 下の手順の `git pull` は、clone したときのブランチ (既定は `develop`) の先頭まで進む。docker ブランチと `bundled` イメージも `develop` の先頭を指す。`main` を追っている場合は、`git pull` は 2.0.0 まで進む。**2.0.0 ちょうどに固定したいなら**、ソースは各手順の `git pull --ff-only` を `git fetch --tags && git checkout 2.0.0` に置き換え (detached HEAD になる)、イメージは `MK_IMAGE=ghcr.io/elythia-network/elythia:2.0.0-bundled` を使う。A の compose は docker ブランチの先頭のものになるが、2.0.0 以降の版の呼び方に合っていれば動く。

構成を選んで進む:

- [A. Docker Compose (docker ブランチ / bundled image)](#a-docker-compose-docker-ブランチ--bundled-image) — `git clone -b docker` で置いた構成
- [B. Docker Compose (ソースからビルド)](#b-docker-compose-ソースからビルド) — リポジトリを clone して `docker-compose.yml` で動かす構成
- [C. Docker Compose (UDS)](#c-docker-compose-uds) — `compose.uds.yaml` で動かす構成
- [D. バイナリ直接実行 (systemd)](#d-バイナリ直接実行-systemd)

自前のリポジトリから `build-with-plugins` を呼んでイメージを作っている場合は、[自前でイメージを作っている場合](#自前でイメージを作っている場合-build-with-plugins) も読む。

## A. Docker Compose (docker ブランチ / bundled image)

compose の project 名 (`mk-image`) は変わらないので、volume (DB とファイル) はそのまま使われる。

1. **イメージを指定しているなら、新しい置き場所に書き換える。** `.env` の `MK_IMAGE` や `docker-compose.override.yml` に `ghcr.io/shiroha-a/mk:...` を書いているなら、`ghcr.io/elythia-network/elythia:...` にする。**書き換えないと、エラーにならないまま以前の置き場所の古いイメージで動き続ける** (以前の置き場所は 2.0.0 の移管で更新が止まった)
2. **手元の変更を `docker-compose.override.yml` に移しておく。** 次の `git reset --hard` は、ブランチのファイル (`docker-compose.yml` など) への手元の変更を捨てる。`git diff` で確かめる
3. **`docker-compose.override.yml` を 2.0.0 の呼び方に直す。** 実行バイナリが `elythia` 1 つになったので、`app` を旧名で書いたものはそのままでは動かない
   - `app` に `command: ["-config", ...]` を書いているなら、先頭に `"serve"` を足す (足さないと、使い方を出して exit 2 で起動しない)
   - healthcheck を書いているなら `["CMD", "/app/elythia", "healthcheck", "-config", ".config/default.yml"]` にする
   - `migrate` サービスの `entrypoint` を `["/app/migrate"]` で書いているなら、2.x の間は互換の symlink で動くが、3.0 で撤去するので今のうちに `["/app/elythia"]` にし、`command` の先頭に `"migrate"` を足す
4. **compose を取り直して、上げる。** migration は `migrate` サービスが `app` の起動前に流す (index を作り終えるまで `app` は起動しない。止まる時間の目安は index の作成時間)

   ```bash
   git remote set-url origin https://github.com/Elythia-Network/elythia.git   # 旧 URL も転送で動く
   git fetch --depth 1 origin docker
   git reset --hard FETCH_HEAD
   docker compose pull
   docker compose up -d
   ```

5. [上げた後に確かめる](#上げた後に確かめる) へ

## B. Docker Compose (ソースからビルド)

compose の project 名はディレクトリ名のまま変わらない (`docker-compose.yml` に `name:` は付けていない) ので、volume はそのまま使われる。frontend の bind mount の元が `third_party/misskey/built` から `frontend/built` に変わるので、**frontend をビルドし直す前に `up -d` しない** (空のディレクトリを mount して 404 を返す)。

`make docker-update` は使わない。1.5.0 のチェックアウトで叩くと、最初の pull が 1.5.0 の Makefile で動き、下の手順と違う形で pull する。

git の設定によっては (`submodule.recurse=true` など)、pull が `third_party/misskey` (1.5.0 が配っている frontend) を消すことがある。その場合、手順 3 の再起動が終わるまで 1.5.0 は frontend を 404 で返す。止めたくなければ、C の手順 1 と同じように先に退避し、mount の付け替えは `docker-compose.override.yml` で行う (追跡されている `docker-compose.yml` を書き換えると、pull が止まる。compose は同じ mount 先の volume を override の側で置き換える)。B の mount 先は `/frontend` と `/client-assets` (C とは違う)。override を書いたら `docker compose up -d` で 1.5.0 を作り直して、退避先を読ませる。その行は手順 3 の前に外す

1. **手元で `docker-compose.yml` を書き換えているなら、控えてから元に戻す。** 2.0.0 の `docker-compose.yml` は `migrate` サービスの entrypoint が `/app/elythia` に、frontend の mount が `./frontend/built` に変わっているので、手元の変更が残っていると `git pull` は `Your local changes ... would be overwritten` で止まる

   ```bash
   git diff docker-compose.yml > docker-compose.local.diff   # 手元の変更を控える
   git checkout -- docker-compose.yml
   ```

   控えた変更は `docker-compose.override.yml` に移す (次から pull を止めない)。`docker-compose.override.yml` があれば、A の手順 3 と同じように 2.0.0 の呼び方に直す
2. **本体とプラグインを pull する。**

   ```bash
   git remote set-url origin https://github.com/Elythia-Network/elythia.git
   git pull --ff-only
   make pull-plugins    # plugins/ に独立リポジトリのプラグインがあるとき
   ```

3. **frontend とイメージをビルドし、起動し直す。** `make docker-rebuild` は `frontend/built` へのビルドとイメージのビルド、`make docker-restart` は起動し直して配信している画面のファイルが実在するかまで確かめる。migration は `migrate` サービスが `app` の起動前に流す (index を作り終えるまで `app` は起動しない)

   ```bash
   make docker-rebuild
   make docker-restart
   ```

4. **片付け。** submodule を外した版を pull しても、`third_party/` は未追跡のディレクトリとして残る。もう読まないので消してよい ([手順](../deployment.md#6-片付け-submodule-を外す版を-pull-した後)。`compose.uds.yaml` が無い構成でも同じ手順でよい)
5. [上げた後に確かめる](#上げた後に確かめる) へ

## C. Docker Compose (UDS)

frontend の bind mount の元が変わるので、**`compose.uds.yaml` を書き換える必要がある** (gitignore されたローカルのファイルなので pull では変わらない)。手順どおりに進めないと frontend が 404 になる。`compose.uds.yaml` がまだ `third_party/misskey` を mount している間は、`make uds-*` が止まって知らせる (`make uds-layout-check`)。

次の手順は [frontend を本体へ取り込んだ版へ上げる](../deployment.md#frontend-を本体へ取り込んだ版へ上げる-3379) と同じで、プラグインの pull と migration の先行適用を足したもの。

1. **配信中の frontend を git の管理の外へ退避し、mount をそこへ向ける。**

   ```bash
   SAVE=/srv/elythia-frontend-save     # git の管理の外。運用に合わせて選ぶ
   mkdir -p "$SAVE"
   cp -a third_party/misskey/built "$SAVE/built"
   cp -a third_party/misskey/packages/frontend/assets "$SAVE/assets"
   ```

   `compose.uds.yaml` の 2 行を、退避した先の絶対パスへ書き換えて、起動し直す。

   ```yaml
         - /srv/elythia-frontend-save/built:/frontend:ro
         - /srv/elythia-frontend-save/assets:/misskey/packages/frontend/assets:ro
   ```

   ```bash
   make uds-restart
   ```

2. **本体とプラグインを pull する。** プラグインは frontend のビルドより前に上げておく (frontend のビルドがプラグインを読み、追従していないプラグインがあると止まる)

   ```bash
   git remote set-url origin https://github.com/Elythia-Network/elythia.git
   git pull --ff-only
   make pull-plugins    # plugins/ に独立リポジトリのプラグインがあるとき
   ```

3. **`frontend/` からビルドする。** 出力先の `frontend/built` はまだどこからも mount されていないので、ビルドの途中でも配信には影響しない。**終わる前や失敗したまま次へ進まない**

   ```bash
   mkdir -p .tmp && rm -f .tmp/uds-frontend-build.log
   nohup setsid sh -c 'make uds-frontend-build; echo "exit=$?"' > .tmp/uds-frontend-build.log 2>&1 &
   until grep -q '^exit=' .tmp/uds-frontend-build.log 2>/dev/null; do sleep 10; done
   tail -n 1 .tmp/uds-frontend-build.log
   ```

   最後の行が `exit=0` でなければ、`.tmp/uds-frontend-build.log` を見て直す (1 で退避した frontend を配り続けているので、急がなくてよい)。

4. **`compose.uds.yaml` を新しいパスへ向ける。** build-arg に `MKGO_FRONTEND_VERSION` が残っていれば消してよい (2.0.0 で廃止した。残っていても使われない)

   ```yaml
         - ./frontend/built:/frontend:ro
         - ./frontend/packages/frontend/assets:/misskey/packages/frontend/assets:ro
   ```

5. **image をビルドする。** **`OK` と出なければ次へ進まない** (失敗したまま進むと、古い 1.5.0 の image で次の手順を流すことになる)

   ```bash
   mkdir -p .tmp && rm -f .tmp/uds-build.log
   nohup setsid sh -c 'make uds-build; echo "exit=$?"' > .tmp/uds-build.log 2>&1 &
   until grep -q '^exit=' .tmp/uds-build.log 2>/dev/null; do sleep 10; done
   tail -n 1 .tmp/uds-build.log | grep -qx 'exit=0' && echo OK || echo "失敗した。.tmp/uds-build.log を見る"
   ```

6. **(任意) migration を先に流す。** UDS の image は起動のたびに migration を流してから起動するので、index の作成に時間がかかると、その間 Elythia が止まる。新しい image で先に流しておけば、次の再起動は待たない。1.5.0 は動いたままでよい

   ```bash
   docker compose -f compose.uds.yaml run --rm --no-deps --entrypoint /app/elythia mkgo \
     migrate -config /app/.config/default.yml -direction up
   ```

   `--entrypoint /app/elythia` を付けるのは、image のビルドに失敗していたときにその場で止めるため (1.5.0 の image には `/app/elythia` が無い)。**流したら、間を空けずに手順 7 へ進む。** この後に 1.5.0 のコンテナが再起動すると、1.5.0 の migration が新しい版の DB に当たって起動できなくなる

7. **起動し直す。** 最後の検証 (配信している画面のファイルが実在するか) が通れば切り替えは終わり

   ```bash
   make uds-restart
   ```

8. **片付け。** `third_party/` を消す ([手順](../deployment.md#6-片付け-submodule-を外す版を-pull-した後))。1 で退避した `$SAVE` は、新しい版で問題が無いことを確かめてから消す
9. [上げた後に確かめる](#上げた後に確かめる) へ

次からの更新は、これまでどおり `make uds-update` でよい (2.0.0 のタグに固定した場合は、追うブランチへ `git checkout` してから)。

## D. バイナリ直接実行 (systemd)

B と同じく、git の設定によっては pull が `third_party/misskey` を消すことがある。1.5.0 のバイナリは frontend だけでなく静的アセットと絵文字も `third_party/misskey` の下から読む (手順 2 の表の 7 つ) ので、消えると手順 5 の再起動までそれらが 404 になる。止めたくなければ、先に `third_party/misskey` を丸ごと退避し、表の 7 つの環境変数を退避先の同じ場所へ向けて 1.5.0 を再起動しておく

1. **本体とプラグインを pull する。**

   ```bash
   git remote set-url origin https://github.com/Elythia-Network/elythia.git
   git pull --ff-only
   make pull-plugins    # plugins/ に独立リポジトリのプラグインがあるとき
   ```

2. **frontend をビルドする。** 出力先は `frontend/built` (Docker で node を動かしてビルドするので、Docker が要る)

   ```bash
   make e2e-frontend-build
   ```

   frontend の場所を環境変数で指定しているなら書き換える (冒頭の注記で退避先へ向けた場合も、必ず表の 2.0.0 の値にするか消す。退避先のままだと、2.0.0 が 1.5.0 の frontend を黙って配る)。指定していなければ、Elythia は作業ディレクトリからの相対パスで新しい既定値を読む。

   | 環境変数 | 1.5.0 の既定値 | 2.0.0 の既定値 |
   |---|---|---|
   | `MISSKEY_FRONTEND_DIR` | `third_party/misskey/built/_frontend_vite_` | `frontend/built/_frontend_vite_` |
   | `MISSKEY_FRONTEND_DIST_DIR` | `third_party/misskey/built/_frontend_dist_` | `frontend/built/_frontend_dist_` |
   | `MISSKEY_CLIENT_ASSETS_DIR` | `third_party/misskey/packages/frontend/assets` | `frontend/packages/frontend/assets` |
   | `MISSKEY_STATIC_DIR` | `third_party/misskey/packages/backend/assets` | `frontend/assets` |
   | `MISSKEY_REPO_ASSETS_DIR` | `third_party/misskey/assets` | `frontend/repo-assets` |
   | `MISSKEY_TWEMOJI_DIR` | `third_party/misskey/packages/backend/node_modules/@misskey-dev/emoji-assets/built/twemoji` | `frontend/node_modules/@misskey-dev/emoji-assets/built/twemoji` |
   | `MISSKEY_FLUENT_EMOJI_DIR` | `third_party/misskey/packages/backend/node_modules/@misskey-dev/emoji-assets/built/fluent-emoji` | `frontend/node_modules/@misskey-dev/emoji-assets/built/fluent-emoji` |

   **`third_party/misskey` を `frontend` に置き換えるだけでは直らない行がある** (下の 4 行は置き場所そのものが変わった)。1.5.0 の `.env.example` を写していれば全部書いてあるので、表のとおりに直すか、消して既定値に任せる。

3. **バイナリをビルドする。** 出力は `built/elythia` (1.5.0 の `built/misskey` は残るので、片付けで消す)。バイナリを別の場所へ置いて動かしているなら、`built/elythia` をそこへ置く

   ```bash
   make build
   ```

4. **migration を流す。** 1.5.0 は動いたままでよい

   ```bash
   ./built/elythia migrate -config .config/default.yml -direction up
   ```

5. **systemd の unit を書き換えて、起動し直す。** `ExecStart` を `elythia serve` にする。引数無しの `elythia` は使い方を出して終了する (exit 2) ので、書き換え忘れはその場で起動に失敗して分かる

   ```ini
   ExecStart=/opt/elythia/elythia serve -config /opt/elythia/.config/default.yml
   ```

   ```bash
   sudo systemctl daemon-reload
   sudo systemctl restart <unit>
   ```

6. **監視やスクリプトを直す。** 旧名のバイナリや flag で呼んでいるものはサブコマンドに直す

   | 1.5.0 | 2.0.0 |
   |---|---|
   | `misskey -healthcheck -config <path>` | `elythia healthcheck -config <path>` |
   | `misskey -config <path> -doctor` / `-fsck` / `-config-dump` | `elythia doctor` / `fsck` / `config-dump -config <path>` |
   | `migrate -config <path> -direction up` | `elythia migrate -config <path> -direction up` |
   | `backfill-<名前> ...` | `elythia backfill <名前> ...` |

7. **片付け。** `built/misskey` と `third_party/` を消す ([手順](../deployment.md#6-片付け-submodule-を外す版を-pull-した後))
8. [上げた後に確かめる](#上げた後に確かめる) へ

## 自前でイメージを作っている場合 (build-with-plugins)

自前のリポジトリから `build-with-plugins` を呼んで、プラグイン入りのイメージを作っている場合:

- `uses:` を `Elythia-Network/elythia/.github/workflows/build-with-plugins.yml@<タグ または コミット SHA>` に書き換える。`mk_repository` を渡しているなら `Elythia-Network/elythia` にする
- `plugins:` に並べたプラグインの ref を、2.0.0 に追従した版へ上げる。本体の ref (`mk_ref`) と組にして上げる (本体だけ、プラグインだけを上げるとビルドが止まる)
- 作ったイメージで動かす構成の手順は、A / C のうち近いものに従う

詳しくは [デプロイ](../deployment.md#リポジトリとイメージの置き場所を移した版へ上げる-3394)。

## 上げた後に確かめる

1. **doctor を流す。** 全項目が `ok` (環境によっては `warn`) であることを見る。nodeinfo の行に `elythia <版>` と出る

   ```bash
   # Docker Compose (TCP / docker ブランチ)
   docker compose exec app elythia doctor -config .config/default.yml
   # Docker Compose (UDS)
   docker compose -f compose.uds.yaml exec mkgo elythia doctor -config /app/.config/default.yml
   # バイナリ直接実行
   ./built/elythia doctor -config .config/default.yml
   ```

2. **画面を開く。** トップと、`/about-elythia` (サーバーのアイコンから開くメニューの「Elythiaについて」) が開くことを見る。ブラウザに Service Worker が残っていると古い画面が出るので、ハードリロードする
3. **プラグインを組み込んでいるなら、起動時のログに `plugin loaded` が組み込んだ数だけ出ていることを見る**

## 連合への影響

- **連合先の一覧に出る名前が変わる。** nodeinfo の `software.name` が `elythia` に、外向きの User-Agent が `Elythia/<版> (<url>)` になる
- **プラグインどうしの連合 (Peer) は、相手が 1.5.0 以前のあいだ止まる。** 宣言の名前が `mkGoPlugins` から `elythiaPlugins` に変わり、どちらも旧名を読まないため。経路は変わらないので、相手が上げれば戻る
- 1.5.0 以前の相手は、2.0.0 を自分と同じソフトとは見なさない (画像プロキシのループ検出、絵文字のメタ情報の取得先の判定)。2.0.0 の側は、旧名の相手も同じソフトとして扱う

## 1.5.0 へ戻す

**1.5.0 の compose・image・バイナリに戻す前に、2.0.0 のまま migration を 8 段戻す。** 1.5.0 の `migrate` は、自分の知らない版 (`116`) まで進んだ DB に当たると `no migration found for version 116` で止まる。compose の `migrate` サービスも UDS の image も起動の前に migration を流すので、戻さないまま 1.5.0 で起動すると、起動そのものが失敗する。

```bash
# A / B (2.0.0 の compose のまま)
docker compose run --rm --entrypoint /app/elythia migrate migrate -config .config/default.yml -direction down -steps 8
# C (動いている 2.0.0 のコンテナの中で)
docker compose -f compose.uds.yaml exec mkgo /app/elythia migrate -config /app/.config/default.yml -direction down -steps 8
# D
./built/elythia migrate -config .config/default.yml -direction down -steps 8
```

> **`-steps` を省かないこと。** 省くと「全部」の意味になり、全テーブルが消える。

> **`-track` の要否は、版の名前ではなく挙動で見分ける。** develop のバイナリも版は `2.0.0` と名乗るので、名前では区別できない。上のコマンドで `-direction down requires -track core or -track local` と出て止まったら、`-track core` を足して流し直す (#3428 以降の `elythia` は down に `-track` を要求する)。逆に `-track` を付けて `flag provided but not defined: -track` で止まったら、`-track` を知らない版なので外す。どちらの止まり方も DB には触れない。
>
> **`-steps 8` は、DB が `116` のときの段数。** それより後の版で起動して migration が先へ進んでいるなら、`SELECT version FROM schema_migrations` の値から `108` を引いた段数にする。戻すのは、DB をその版まで進めたバイナリで行う (2.0.0 のバイナリは自分の知らない版で止まる)。`116` より先の分の down がデータを失わないかは、その版の文書で確かめてから流す。

8 段の内訳は index の削除 7 本と、`000116` で新しい URL にした `meta.repositoryUrl` / `meta.feedbackUrl` を以前の既定値に戻すもの 1 本で、データは失われない (2.0.0 の `migrate` で `116` から `108` に戻したあと、1.5.0 の `migrate` が通ることを確かめてある)。

- **戻したら、間を空けずに 1.5.0 で起動する。** 間に 2.0.0 が起動し直すと、migration がまた進む (C の UDS の image と、A / B の `migrate` サービスは、起動のたびに migration を流す)。C は、1.5.0 の image を作り終えてから、動いている 2.0.0 のコンテナの中で戻し、すぐに起動し直す
- **2.0.0 に合わせて直したものは、1.5.0 の形へ戻す。** compose の override (`serve` / healthcheck / `migrate` の entrypoint)、`.env` の `MK_IMAGE`、`compose.uds.yaml` の mount、systemd の unit と `MISSKEY_*`。直したままだと 1.5.0 は起動しない (1.5.0 のイメージに `/app/elythia` は無い)
- **A** は、1.5.0 の compose と以前の置き場所の 1.5.0 のイメージに戻す。2.0.0 の compose の既定のイメージは新しい置き場所の `bundled` (develop の最新) なので、compose を戻さないと 1.5.0 にならない

  ```bash
  curl -fsSL -o docker-compose.yml https://raw.githubusercontent.com/Elythia-Network/elythia/1.5.0/docker-compose.image.yml
  # .env の MK_IMAGE を ghcr.io/shiroha-a/mk:1.5.0-bundled にする (無ければ足す)
  docker compose up -d
  ```

- **B / C / D** は `git checkout 1.5.0` で戻す。frontend をビルドしたチェックアウトでは、先に `git checkout -- frontend/packages/i18n/src/autogen/locale.ts` を流す (1.5.0 には無い生成物なので、変更が残っていると checkout が止まる)。片付けで `third_party/` を消していたら、`git submodule update --init` で 1.5.0 の frontend のソースを取り直し、1.5.0 の手順で frontend をビルドし直す (B: `make docker-rebuild`、C: `make uds-frontend-build` → `make uds-build`、D: `make e2e-frontend-build`)。C は、退避した `$SAVE` が残っていれば mount をそこへ向けてもよい。プラグインは、追従する前のタグ `pre-elythia` に戻す
- C で先に `git checkout 1.5.0` すると、2.0.0 が mount している `frontend/packages/frontend/assets` が消え、切り替えるまでの間その中身が 404 になる
- 戻し方に迷ったら、上げる前に取った DB のバックアップと、1.5.0 のときの構成に戻すのが確実
