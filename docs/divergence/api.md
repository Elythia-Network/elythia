# 純正 Misskey との差分: API

[差分カタログの目次](../divergence.md) にある分類と基準 (Elythia と追従している本家の版) は、このファイルにも当てはまる。

## ピン留めノートと作者ロックの公開境界 (#3310)

プロフィールに現在ピン留めされているノートは、作者が明示的に公開したものとして扱う。ただし例外は `public` / `home` に限り、`followers` / `specified` の通常の可視性 ACL、ブロック等の既存制約、匿名閲覧に対する `requireSigninToViewContents`、サーバー全体の visitor 制限は迂回しない。

- 匿名: 現在ピン留め中、`public` / `home`、かつ `requireSigninToViewContents=false` と確認できる場合だけ、`makeNotesHiddenBefore` / `makeNotesFollowersOnlyBefore` を迂回する。
- 認証済み: 現在ピン留め中の `public` / `home` は作者ロックを迂回する。ログインしただけで `followers` / `specified` を読めるようにはならない。
- 状態遷移: ここでいう「現在ピン留め中」は user profile の `user_note_pining` にリクエスト時点で行があることを指し、frontend の gitlink 等とは無関係である。unpin、visibility 変更、`requireSigninToViewContents` 変更は primary の現在値で判定し、保存済みノートの visibility や作者設定は変更しない。
- 適用経路: `notes/show`、利用者を UserDetailed で返す応答の `pinnedNotes`、ノート permalink の SSR metadata。`pinnedNotes` はすべて `internal/api/users` の `fillPinnedNotes` で組み、同じ `notehide.HideProfilePinnedNotes` を通す (#3330)。通る経路は、単体の `users/show`、一覧の `users` / `pinned-users` / `users/search` / `users/search-by-username-and-host` / `users/show` (`userIds` 指定) / `users/recommendation` / `users/get-frequently-replied-users` / `users/followers` / `users/following` / `blocking/list` / `mute/list` / `renote-mute/list` / `hashtags/users` / `federation/users` / `federation/followers` / `federation/following` / `following/list` / `roles/users` / `admin/show-users` / `admin/roles/users` / `admin/abuse-user-reports` / `admin/show-moderation-logs`、単体の `ap/show` / `admin/accounts/find-by-email` / `admin/update-proxy-account` / `auth/session/userkey` / miauth の check / `page-push` の `pageEvent` / `blocking/create`・`delete`、main stream の `follow` / `unfollow` と同名の Webhook。一覧では本家 `packMany` と同じく、匿名の閲覧者にはピン留めを載せない (`pinnedNoteIds` / `pinnedNotes` は空)。`admin/abuse-user-reports` と `admin/show-moderation-logs` は本家と同じく閲覧者なし (`packMany(users, null)`) で組むので、モデレーターが呼んでもピン留めは空になる。`find-by-email`・`userkey`・miauth の check は本家と同じく閲覧者なし (`pack(user, null)`) として判定する。`update-proxy-account` は proxy 自身を、`page-push` はページの持ち主を閲覧者として判定する (本家 `pack(proxy.id, proxy)` / `pack(me.id, {id: page.userId})`)。pin lookup または作者設定の確認に失敗した匿名の pin 例外は fail-closed とする。ActivityPub Note / Note activity / user outbox / featured collection は連合互換性のため従来どおり `visibility` と `localOnly` だけで公開可否を判定し、この Web 閲覧向け例外の対象外とする。

これは vanilla Misskey の一般的な visibility 判定を置き換えるものではなく、Elythia が pin を作者の明示的な公開意思として一貫して扱うための限定的な divergence である。

## 作られてから日の浅いアカウントからのフォロー (#3466)

本家の PR 17998 (2026.10.0 より後) の設定を、同じ API で取り込んでいる。`user_profile` の `followApprovalLocalSeconds` / `followApprovalRemoteSeconds` (秒、`null` と 0 は止めない) に満たないアカウントからのフォローは、フォローされる側がローカルの人なら止める。鍵アカウント・Bot に慎重・サイレンスしたホストで既に承認待ちになるフォローには関係しない (本家と同じ)。自分がフォローしていて `autoAcceptFollowed` が有効な相手は、期間に関係なく通常どおり成立する (本家と同じ)。

本家と違うのは 2 点。

| 項目 | 本家 | Elythia |
|---|---|---|
| リモートの人の経過時間 | ID の日時 (このサーバーがその人を初めて知った日時) から数える。初めてやりとりする相手は、何年も使われているアカウントでも全員が新しい扱いになる | `user.accountCreatedAt` (#3465。actor の `published` か、Misskey 系の相手の `users/show` の `createdAt`) があればそれで数え、無ければ本家と同じく ID の日時で数える。フォローを受け取ったときに列が空なら一度だけ取りに行く (#3465)。ローカルの人は本家と同じ (ID の日時 = 登録日) |
| 止め方 | フォローリクエストにして、`receiveFollowRequest` の通知を出す | `user_profile.followApprovalAction` で選ぶ。`request` (既定) は本家と同じ。`silentRequest` はリクエストにするが通知を作らない (リクエストの一覧と main stream のイベントは通常どおり)。`silentFollow` はフォローを成立させ、`follow` の通知を作らず、`silent_follow` に記録して `following/silent/list` で後から確かめられるようにする。**Webhook (`followed`) と main stream のイベントは止めない** — 前者は利用者が自分で設定した連携、後者は画面の状態の更新なので |

- 相手の ID の形式が読めず日時を出せないときは止めない。Elythia が作った ID ではない (TS 版の古い形式など) ときだけ起きる。止める側に倒すと、その人からのフォローが期間に関係なく永久に止まる
- **鍵アカウントを解除すると、溜まっていたフォローリクエストを承認する。** #3466 より前の Elythia には無かった動きで (本家は以前から持っていた)、これで本家に揃えた。**承認するのは期間の条件以外で止まったものも含む** — Bot に慎重 (`carefulBot`) やサイレンスしたホストからのフォローで申請中になっていたものも、本家と同じく解除で承認される
- 一括承認の条件は本家と同じ。期間の条件に当たる人のリクエストは残し (止め方に関係なく。解除で静かな成立に変えることはしない)、自分が既にフォローしていて `autoAcceptFollowed` が有効なら承認する。処理中に取り消されたリクエストは飛ばす。**既にフォローが成立しているリクエスト (下の「フォローと申請が両方ある行」) は、申請を消すだけで承認として扱い、残りを止めない** (本家は local のフォロワーではここで落ちる)。同時に 2 回解除しても、片方が承認した分で止まらない
- **一括承認は `i/update` の中で同期的に走る** (本家と同じ。本家も await してから応答する)。申請が多いと、その分だけ `i/update` の応答が遅れる。**途中で失敗しても `i/update` は成功を返す** (本家は 500)。設定は保存済みで、残ったリクエストは `following/requests/list` から手で承認できる
- **即フォローが成立したときは、同じ組の申請を消す** (本家 `insertFollowingDoc` と同じ)。期間の設定を外した後や期間を過ぎた後にフォローし直すと、前の申請が残ったまま成立する経路があり、消さないと「フォロー済みかつ申請中」の行になって、承認が following の一意制約で 500 になっていた。`following/requests/accept` も、既にフォロー済みなら申請を消して成功を返す。**このとき、残っていた申請に対する Accept は相手へ送らない** (本家はリモートのフォロワーへ送る)。フォローが成立したときに Accept は送ってあるので、相手の状態は変わらない。**同じ申請を同時に承認したとき** (二度押し、鍵の解除の同時実行) も、following の一意制約に当たった側を「既にフォロー済み」と同じく成功として扱い、500 にしない。申請を先に消した側より後に読みに来た方は、本家と同じく申請が無いエラー (`NO_FOLLOW_REQUEST`) になる。一括承認はこれを飛ばすので止まらない
- 「静かにリクエストにする」でも、受け取った申請があることはナビゲーションのフォローリクエストの印 (MeDetailed の `hasPendingReceivedFollowRequest`) に出る。止めるのは通知 (`receiveFollowRequest`) だけ。フォローリクエストの画面は、受け取った申請があれば鍵アカウントでなくても「受け取った」タブを先に開く
- 相手が作成日時を偽ることは、この機能では防がない (#3465 の決定)

## Page の公開範囲 (#3479)

Page に作者だけが見られる `private` を足し、公開範囲を `public` / `private` の 2 値にした。派生版の一つが同じ形で入れている。本家の Page には列 (`public` / `followers` / `specified`) だけがあり、作成時は必ず `public` を書く。公開範囲を選ぶ API も画面も無い。

| 項目 | 本家 | Elythia |
|---|---|---|
| `pages/create` / `pages/update` の `visibility` | 受け付けない | `public` / `private` を受け付ける。それ以外は `INVALID_PARAM`。create で省くと `public`、update で省くと今の値のまま |
| Page の応答の `visibility` | 出さない | 出す (作者以外に返るのは `public` の Page だけ) |
| `pages/show` | 公開範囲を見ない | `private` の Page は作者以外に `NO_SUCH_PAGE` (ID と名前のどちらで引いても) |
| `pages/like` | 公開範囲を見ない | `private` の Page は作者以外に `NO_SUCH_PAGE` |
| `pages/unlike` | 公開範囲を見ない | `private` の Page を like していない他人には `NO_SUCH_PAGE` (`NOT_LIKED` では存在が分かるため)。公開中に like した人は外せる |
| `page-push` | 公開範囲を見ない | `private` の Page は作者以外に `NO_SUCH_PAGE` (作者のストリームにイベントを送らない) |
| `users/show` などの `pinnedPage` / `pinnedPageId` | 公開範囲を見ない | `private` の Page は、作者以外にはどちらも `null` (ID が出ると、private の Page を持っていることが分かる)。Page を読み出せなかったときも、作者以外には `pinnedPageId` を出さない。Page が削除済みなら `pinnedPageId` だけを出す (本家は列の FK の `ON DELETE SET NULL` で ID が消えるが、Elythia の DB にはこの FK が無い。#3479 より前からの差) |
| `users/pages`・`pages/featured` | `public` だけを出す | 同じ (`private` は作者本人が見ても出さない。作者は `i/pages` とエディタで見る) |
| `/@<user>/pages/<name>` の HTML の metadata | 公開範囲を見ずに題名・要約・アイキャッチ・Page の ID を出す。公開範囲で変えるのは `Cache-Control` だけ | `private` の Page は、Page が無いときと同じ応答にする (`Cache-Control` も同じ)。HTML は閲覧者を区別しないので、作者にも既定の表示になる |
| `i/page-likes` | 公開範囲を見ない | 他人の `private` の Page は一覧から外す (like の行は残すので、`pages/unlike` で外せる) |
| `pages/update` / `pages/delete` を作者以外が呼んだとき | `ACCESS_DENIED`。ただし `pages/delete` はモデレーターなら他人の Page も消せる | 公開の Page は `ACCESS_DENIED`、`private` の Page は `NO_SUCH_PAGE`。**`pages/delete` はモデレーターでも作者以外は通さない** (#3479 より前からの差) |
| 画面 | 無い | エディタの「公開範囲」で選ぶ |

- **#3479 より前は、`followers` / `specified` も受け付けていた。** 初期の実装から入っていた独自の引数で、ここにも `elythia-js` の型にも載っていなかった。判定はどちらも「作者以外には見せない」だった。`000121` がこの 2 値の行を `private` にする (見える範囲は変わらない)。これらを渡すクライアントは `INVALID_PARAM` になる
- 3 値のまま画面を作らなかったのは、`specified` には相手を選ぶ画面が、`followers` には Page の全経路でのフォロー判定が要るため
- 連合には影響しない (Page は ActivityPub で配らない)

ガードと衝突し、非公開 URL の構成では取れず、DB 上の行と実体の対応も確かめられないので、`storedInternal` を見て実体のあるバックエンドから直接読む。**`originalUrl` は複製の `url` と一致させる** — drive の孤児 cleanup が `emoji.originalUrl = drive_file.url` または `publicUrl = url` を参照保護の条件にしているので、webpublic だけを入れると保護が外れて消される。**途中で失敗したら作ったものを消す** (複製の失敗 → 絵文字を作らず申請は pending のまま / 絵文字の作成失敗 → **載ったかを読み直してから**複製を削除 (#3019) / 競合に負けた → 絵文字と複製の両方を削除)。**読み直せないときの倒し方が 2 cascade して消えるので、ローカルの使い捨てアカウントを通報に使って削除すると窓を越えられる (1 回のポップアップにアカウント 1 つ。一覧は 1 件のままなので押し出しは起きない。リモートの `Delete(actor)` は論理削除で通報が残るので、この経路は無い)。(c) **既存を作り直さない通報**: 同じ通報者が同じ相手を未解決のまま重ねたもの / リモートからの通報で、同じホストから未解決の通報が既にあるもの。**「自分より古い」id の未解決で判定する** — 「自分以外」だと並行して入った 2 件がお互いを見て両方黙る。ローカルの通報はホストで絞らない (reporterHost が NULL で全員が同じ「ホスト」になる)。**既読位置を判定に使わない** — frontend は通知欄を表示している間、通知が届くたびに `readNotification` を送って既読にするので、「未読があれば作らない」形は通知欄を開いているモデレーターにだけ一切効かない (初稿がその形で、敵対的レビューで指摘された)。**既存が無ければ必ず作る** — 押し出された / 参照先の通報が消えた (read 時に drop される) ときに見送ると、見送った通報が見える場所がどこにも無くなる。check と create は受信者ごとに Redis のロック (所有者を確かめて外す) で直列化する (無いと並列に投げるだけで全員が「既存なし」を見て全員が作る)。自分宛て・ロール単位の opt-out はロックの前に判定する (作らない呼び出しがロックを取ると、同時に来た別の通報が見送られて誰にも届かない)。**作り直さなかった通報は read 時の `unresolvedCount` (インスタンス全体の未対応の件数) にだけ現れる** — 残っている 1 件が対処済みでも後続が残っていることは出るが、その 1 件が既読のまま他の通知の下に沈んでいれば、バッジもポップアップも先頭への移動も無い。特に (c) に当たる通報は窓が明けても作り直さないので、古い通報が未解決の間は通知欄から気付きにくい (管理画面の一覧には出る)。数えられなかったときは 0 ではなく**載せない** (0 だと「未対応なし」と読める)。REST はページで 1 回だけ数え、失敗は状態の lookup と同じく 500 (#2792)。**lookup の失敗は作り直す側へ倒す** — 作り直さない側に倒すと、新しい通報が先頭に上がってこない |
| `notifications` / `i/notifications` の `type` | `emojiApplicationReceived` | カスタム絵文字の登録申請が出されたことを**審査できる人**へ知らせる (#2987)。**upstream には申請という概念自体が無い。** **宛先はモデレーターではない** — 審査 endpoint は `RequireRolePolicy(canManageCustomEmojis)` で、`HasRolePolicy` が短絡するのは root と管理者だけ (モデレーターは短絡しない)。モデレーターへ配ると「届いたのに押せない」「押せるのに届かない」が同時に起きる。宛先の列挙は `role.GetUsersWithPolicy` で、**割り当て型ロールだけを見る** — conditional role は assignment を持たず、列挙するには全ユーザー走査が要る (`GetModerators` も同じ制限)。**base policy が true でも全員へは広げない** — `meta.policies` でそのキーを全員に与える設定は可能だが、申請 1 件ごとに全員へ通知が飛ぶ。`notifier` は申請者で、Extra は `applicationId` だけ。名前・ライセンス・画像は read 時に申請の行から引き直す (#2868 と同じ形。通知へ複製すると申請を消しても Redis に残る)。**処理済みかどうかも read 時に出す** — 無いと他の人が処理済みの申請に二重で当たる。申請が消えていたら通知ごと drop する。**read 時に権限を再確認する** (fail-closed) — 権限を失った元管理者が通知欄から申請の存在を見続けられないようにする。**通知の導線は `/custom-emojis-manager?tab=applications` へ送る** — `/admin/*` は `iAmModerator` gate を持つので、モデレーターではない絵文字管理者が `/admin/emojis` へ行くと not-found になる |

### 1-1c. リクエストパラメータの additive

upstream にもある endpoint に、Elythia が任意パラメータを足しているもの。**足すだけ**なので
upstream 由来のクライアントはそのまま通る (省略時は upstream と同じ挙動)。

| endpoint | パラメータ | 内容 |
|---|---|---|
| `admin/abuse-user-reports` | `reportId` | 通報の通知から該当の 1 件を開くための additive パラメータ (#2868)。**指定時は `state` / `reporterOrigin` / `targetUserOrigin` / cursor の絞りを無視する** — 一覧の既定は `state=unresolved` なので、他のモデレーターが先に解決した通報に通知から飛べなくなる。1 件を名指しで引く以上、絞り込みは意味を持たない。存在しない ID は 404 ではなく空配列 (一覧 endpoint なので) |
| `admin/queue/jobs` | `limit` / `page` | 1 ページの件数 (既定 30、上限 100) とページ番号。**指定したときだけ効く** (`limit: 0` は省略と区別できないので省略扱い) — 省略時は upstream と同じく state ごとに新しい順で最大 101 件 (`getJobs(types, 0, 100)` は終端を含む) を state の指定順に連結して返す (#3167)。指定時は**全 state 合計**で `limit` 件に切る (state を順に詰めるので、後ろの state は前が埋めると出ない)。同梱フロントは指定しない。以前は省略時にも既定の 30 件が合計に効き、しかも古い順だったので、「すべて」タブが古い完了済みだけで埋まって失敗が 1 件も見えなかった |
